# 医院对接会议准备（2026-09-26）

> 本文档用于与口腔医院/医生对接前的自我梳理与会中参考。核心目标：拿到对方「全新结构、更贴合现实应用」的病例数据，并敲定数据之外我们还需要对方提供的支持。

---

## 1. 项目一句话定位

**LLM 驱动的虚拟标准化患者（Virtual Standardized Patient）教学训练平台**，面向口腔医学教育。学生通过与 AI 患者自然对话反复练习临床问诊技能，问诊结束后系统自动给出**双轨评估**：诊断能力（Station 4）+ 沟通能力（MAAS-Global）。

**定位边界**：系统是真人标准化患者（SP）的**补充练习工具**，而非替代真人 SP——这条定位在对外沟通时需始终强调，以降低医院方的接受度顾虑。

---

## 2. 背景与核心目的

### 2.1 要解决的问题

医学教育中，标准化患者（SP）是训练医学生临床问诊能力的关键手段，但真人 SP 存在三大困境：

| 困境 | 表现 |
|---|---|
| **成本高昂** | 招募、培训、排班、薪酬——单所医学院年均 SP 支出可达数十万元 |
| **资源稀缺** | 合格 SP 数量有限，每位学生每学期仅 2–3 次练习机会 |
| **一致性差** | 同一病例由不同 SP 扮演时表达差异大，评分缺乏标准化基线 |

口腔科的 SP 需求尤为突出：口腔问诊有独特的 OLDCARTS 框架、牙位描述体系和检查流程，且中国口腔执业医师资格考试（Station 4）对问诊能力有明确评分标准。

### 2.2 解决方案（四点核心价值）

| 价值 | 说明 |
|---|---|
| **低成本** | 一次部署，无限次复用，边际成本趋近于 API 调用费用 |
| **可扩展** | 支持大量学生并发练习，不受物理时空限制 |
| **可控一致** | 同一病例的核心医学事实恒定，人格风格可调但**不影响医学事实** |
| **即时反馈** | 问诊结束后自动生成双轨评估报告（诊断 + 沟通） |

### 2.3 用户角色

| 角色 | 规模 | 核心需求 |
|---|---|---|
| 医学生（口腔专业） | 50–200 人/届 | 安全环境反复练习问诊，即时获得评估反馈 |
| 临床带教老师 | 5–15 人 | 查看学生问诊记录，定位薄弱环节 |
| 教学管理人员 | 1–3 人 | 管理病例库、查看使用统计、导出教学数据 |

## 3. 现状

### 3.1 已跑通的完整闭环（MVP 已实现）

```
教师准备病例 → 学生选择病例 → AI 患者开场 → 学生逐轮提问 →
AI 患者回答（流式） → 学生提交诊断 → 系统自动评估 → 学生查看评估报告
```

已具备能力：
- **AI 患者仿真（4 步流水线）**：意图分类 → 信息检索（结构化字段查找，非 RAG）→ 回答生成（流式）→ 事实校验。**零幻觉设计**：信息不足时回答「不清楚/不知道」，绝不编造医学事实。
- **4 级信息分层披露**：患者事实按 Tier 1–4 分级，Tier 4（诊断/治疗方案）**永久隐藏**，学生须自行诊断。
- **双轨智能评估**：Station 4 诊断评分 + MAAS-Global 沟通评分，并行执行。
- **完整前后端**：登录（工号制）→ 病例选择 → 问诊对话（SSE 流式）→ 诊断提交（5 字段）→ 评估报告 → 历史回放。
- 会话轮数上限（默认 12 轮，对标执医考试时间约束）。

### 3.2 当前缺口

- **病例数据缺失**：病例库当前为空（旧数据已下线），正待医院方提供全新结构化病例数据。
- 人格风格系统（81 种组合：焦虑 × 话量 × 信任度 × 语言风格）基础设施已就绪，尚未接入会话创建流程。
- 教师管理端、病例审核编辑、批量导入自动化等属后续阶段。

## 4. 当前系统「预期」的病例数据结构（对接基准）

这是当前系统 Agent 按固定字段路径取数时所假设的结构。**新数据无论什么格式，最终都需要能映射到这套语义**（字段名可不同，但「哪些信息分哪一层披露」的语义要对齐）。

```
basic_info           { gender, age_range, visit_type }
chief_complaint      "左下后牙反复疼痛一周，加重两天"           # Tier 1
present_illness      { onset, duration, character,               # Tier 2
                       aggravating_factors, relieving_factors, radiation }
past_history         { dental, medical, allergy, medication }    # Tier 2
oral_examination     { inspection, percussion, palpation,        # Tier 3
                       mobility, thermal, periodontal }
auxiliary_examination { xray, cbct }                             # Tier 3
diagnosis            { primary, secondary, icd_code }            # Tier 4 永久隐藏
treatment_plan       { emergency, definitive, restoration, notes } # Tier 4 永久隐藏
```

**层级披露机制（考核公平性的核心）**：

| 层级 | 内容 | 披露条件 |
|---|---|---|
| Tier 1 | 主诉 / 就诊原因 | 开场即披露 |
| Tier 2 | 现病史详情 + 既往史 | 学生主动询问症状/病史后披露 |
| Tier 3 | 口腔检查结果 + 辅助检查 | 学生询问检查后披露 |
| Tier 4 | 诊断 + 治疗方案 + ICD 编码 | **永久隐藏，学生须自行推导** |

**诊断报告（学生提交的 5 字段）**：主诊断、鉴别诊断、诊断依据、建议检查、治疗方案。

## 5. 我们对医院/医生的需求

1. **新的结构化病例数据（本次核心）** —— 需明确：字段清单与语义、层级（哪些信息必须由学生自己问出来）、粒度与数量、覆盖的疾病类型/科室/难度。
2. **「隐藏答案」的界定** —— 是否仍保留「诊断/治疗方案」这一层作为学生必须自主推导、系统永不透露的考核边界（对应现 Tier 4）？
3. **临床审校** —— 结构化后的病例，是否由医生把关临床准确性？（现系统**无**教师审核层。）
4. **人工评分（论文一致性实验）** —— 需招募 3 位口腔带教老师，对 10 份学生问诊记录独立评分，与系统双轨评分计算 ICC / Pearson r / Cohen's κ（目标 ICC ≥ 0.75、r ≥ 0.80）。这是验证「AI 评分可信」的关键实验。
5. **评分标准确认** —— 现用 Station 4（5 维，权重 30/15/15/25/15）+ MAAS-Global 的口腔科改编版，需医生确认这套改编是否符合真实临床带教实际。
6. **隐私合规** —— 源数据须去标识化/脱敏（旧数据因含 PHI 从未进 git）。
7. **演示与部署需求** —— ≥3 个口腔演示病例、一套预设的完整「问诊 + 评估」演示、汇报 PPT；长期规划为 Docker 部署 + PostgreSQL 迁移 + 管理员手册。

## 6. 待确认问题清单（会上逐条问）

1. 新数据的**字段结构**和**层级语义**是什么？是否仍有「不能透露的诊断/治疗」这一层？
2. 字段里的检查项（视诊/叩诊/探诊/松动度/扪诊/冷热诊、X 光/CBCT）是否沿用，还是有新的、更贴合现实的检查维度？
3. 病例**数量、疾病类型、科室、难度分级**的目标是多少？
4. 谁负责**临床审校**？审校标准（什么算「合格病例」）是什么？
5. 评分 rubric（Station 4 + MAAS-Global 口腔改编）是否需要医生校订？
6. 评估目前只拿「主诊断 + 根治方案」当评分标准答案；次要诊断、ICD 编码、急诊处理、修复方案、注意事项**是否也要纳入评分**？（现系统会静默丢弃这些字段。）
7. 能否提供 3 位老师做**人工评分一致性实验**？
8. 数据**去标识化/脱敏**由谁负责、标准是什么？
9. 系统在医院的**定位与接受度**（补充练习工具 vs 替代 SP），演示形式（≥3 病例 demo）？

## 7. 会议议程（建议）

| 环节 | 内容 | 时长 |
|---|---|---|
| 1 | 双方自我介绍 + 项目定位对齐 | 10 min |
| 2 | 我方讲现状：已跑通闭环 + 当前预期数据结构（见 §3、§4） | 15 min |
| 3 | **对方讲新数据**：格式、字段、层级、数量、疾病覆盖 | 30 min |
| 4 | 逐字段映射：新结构 vs 现系统 schema，识别差异与「考核边界」等价物 | 20 min |
| 5 | 敲定「我们还需要什么」：临床审校、人工评分、rubric 确认、脱敏 | 15 min |
| 6 | 待办与时间表 | 10 min |
