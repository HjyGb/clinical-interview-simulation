# 模型选型说明

> 写于 2026-10-10，在发现原 pro 模型 `deepseek-v3.1` 已被百炼下架、且账户一度欠费之后。
> 本文记录：项目到底需要几种"模型角色"、怎么选、当前用什么、落地需要什么规模。
> 与 [positioning-and-principles.md](positioning-and-principles.md) 的 P3（引擎/内容分离）互为补充：模型选型是"引擎"的一部分，不绑定科室内容。

---

## 1. 项目有三种模型角色，需求完全不同

| 角色 | 干什么 | 频率 | 需要的"推理" | 上下文 | 成本敏感度 |
|---|---|---|---|---|---|
| **患者生成**（pro） | 把 allowed_facts 说成自然口语 | 每轮一次，流式 | **低**——患者不该"聪明"，要自然+忠实 | 全人格+24轮历史 ≈ 3–6K | **高**（每轮都跑） |
| **事实选择**（lite） | 问句 → 事实 ID | 每轮一次 | **中**——是分类，可靠 > 聪明 | 1–2K | 高 |
| **评估/评分**（endgame） | 读全对话，判诊断+沟通 | 每会话一次 | **高**——真需要临床判断 | 全对话 5–10K | **低**（低频） |

**核心洞察：三种角色想要的"推理效果"是相反的。**

- 患者生成**不该**用强推理模型——患者说得太"聪明"反而假；且推理模型首 token 慢（实测从 ~0.25s 掉到 ~2.5s，学生体感是冷场），register 也不对。
- 评估**恰恰**是唯一该用强推理模型的地方——那是真正要"想"的任务。
- 事实选择用 cheap 非推理模型在 temp=0 下最稳。

现有 pro/lite 两档架构天然对应前两个角色；**评估值得单独第三档**，不要硬塞进 pro。

## 2. 选型四维度

| 维度 | 患者生成 | 事实选择 | 评估 |
|---|---|---|---|
| 推理能力 | 低 | 中 | 高 |
| 上下文 | 3–6K | 1–2K | 5–10K |
| 延迟 | 极敏感（流式） | 敏感 | 不敏感（一次） |
| 成本 | 敏感（高频） | 敏感（高频） | 不敏感（低频） |

**上下文结论**：全项目最大需要 ~10K token，**32K 窗口绰绰有余**。当前可用的 `qwen-plus` 等都在 128K 级别，`qwen-long`（百万级）对本项目是杀鸡用牛刀。

## 4. 选型方案

### 现阶段（跑通 M4/M5）

| 角色 | 选型 | 理由 |
|---|---|---|
| lite 事实选择 | `qwen-turbo`（保留） | 便宜、快、temp=0 下稳，已验证 100% |
| pro 患者生成 | **`qwen-plus`**（替换 deepseek-v3.1） | 非推理、中文口语好、成本适中 |
| （可选升级） | `qwen-max` | 口语更自然、更贵——先 plus 跑通，不够再升 |

### endgame（加评估后）

| 角色 | 选型 | 前提 |
|---|---|---|
| 评估 | `qwen-max`（非推理，最稳）**或** `deepseek-v4-pro-0813` / `qwen3.5-plus`（推理） | 用推理模型前**必须先修** `llm_client` 不读 `reasoning_content`/不查 `finish_reason` 的缺陷（见 memory：deferred-evaluator-failure-handling） |

**顺序建议**：评估先用 `qwen-max` 非推理跑通（无需先修缺陷、零额外风险），等 rubric 与流程定形后再决定是否上推理模型。

## 5. 真正落地需要什么"规模"

**结论：这个项目对"参数量"的需求没有想象中高。** 真正决定成败的是三件事：

1. **对话侧中等模型足够。** 患者模拟本质是"指令遵循 + 中文口语流利 + 忠实给定事实"，不是复杂推理。
   像不像人更多取决于 prompt 与行为规则（M4 已验证：改 prompt 的效果远大于换模型），不是参数规模。
2. **评估侧的瓶颈是 rubric，不是模型。** 评估准确率约 70% 取决于评分标准写得好不好
   （需医院医生一起打磨），模型只占 30%。好 rubric + `qwen-max` 胜过烂 rubric + 前沿模型。
3. **上下文窗口需求很小**（≤10K），32K 足够。

**真正决定"规模"的是部署形态，尤其是 PHI：**

| 场景 | 规模方案 |
|---|---|
| 开发/MVP | 百炼 API：`qwen-turbo` + `qwen-plus`，零部署 |
| 医院内网 + 敏感病历 | 私有化：百炼专属部署，或自托管开源权重（Qwen-72B/122B 或 DeepSeek-V3 量级） |
| 高并发（全班同练） | 对话侧便宜模型扛并发，评估侧按需排队，不与生成抢配额 |

## 6. 落地动作顺序

1. **现在**：`.env` 改 `LLM_MODEL_PRO=qwen-plus`，跑通 M4/M5。
2. **评估启动时**：加第三档配置 `LLM_MODEL_EVAL=qwen-max`，评估独立用强模型。
3. **rubric 定形后**：再决定是否上推理模型；要上先修 `llm_client` 的 `reasoning_content` 缺陷。
4. **真落地**：按 PHI 要求定私有化部署形态（与医院对接会议一起定）。

## 附：错误码对照（本次排查沉淀）

| 错误码 | HTTP | 含义 |
|---|---|---|
| `Arrearage` | 400 | **账户级**欠费/状态异常，会拦住所有模型（含还有额度的）。任何阿里云产品未结清都可能触发 |
| `AllocationQuota.FreeTierOnly` | 403 | **某个模型行**的免费额度耗尽 + 账号在"用完即停"模式，不再计费 |
| `model_not_found` | 404 | 模型 ID 不存在/已下架 |

- 免费额度是**按模型行**单独给、90 天有效、用完不会停（除非开"用完即停"）。
- "用完即停"（安心模式）开着时，额度耗尽就 403，运行中的系统会中途撞 403——本项目已有 `error` 兜底
  （患者说"没听清"并记 error 日志），不会静默坏数据。
