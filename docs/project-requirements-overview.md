## 一、项目背景与动机

### 1.1 核心问题

医学教育中，**标准化患者（Standardized Patient, SP）** 是训练医学生临床问诊能力的关键教学手段。然而，真人 SP 面临三大困境：

| 困境 | 具体表现 |
|---|---|
| **成本高昂** | 招募、培训、排班、薪酬——单所医学院年均 SP 支出可达数十万元 |
| **资源稀缺** | 合格 SP 数量有限，每位学生每学期仅有 2–3 次练习机会 |
| **一致性差** | 同一病例由不同 SP 扮演时表达差异大，评分缺乏标准化基线 |

**口腔科**的 SP 需求尤为突出：口腔问诊有其独特的 OLDCARTS 框架、牙位描述体系和检查流程，且中国口腔执业医师考试（Station 4）对问诊能力有明确的评分标准。

### 1.2 解决思路

利用**大语言模型（LLM）**构建虚拟标准化患者 Agent，实现：
- **低成本**：一次部署，无限次复用，边际成本趋近于 API 调用费用
- **可扩展**：支持数千学生并发练习，不受物理时空限制
- **可控一致**：同一病例的核心事实始终一致，人格风格可调节但不影响医学事实

## 三、业务功能需求

### 3.1 核心业务流程

```
教师准备病例 → 学生选择病例 → AI患者开场 → 学生逐轮提问 →
AI患者回答 → 学生提交诊断 → 系统自动评估 → 学生查看评估报告
```

### 3.2 功能模块需求

#### 模块 A：病例管理

| 需求编号 | 需求描述 | 优先级 |
|---|---|---|
| A1 | 支持从原始病历数据批量导入生成标准化病例 | P0 |
| A2 | 病例包含完整的结构化信息：基本信息、主诉、现病史、既往史、口腔检查、辅助检查、诊断、治疗方案 | P0 |
| A3 | 病例按科室分类（当前以口腔科为主，架构需支持多科室扩展） | P1 |
| A4 | 病例支持难度分级（初/中/高级），便于分阶段教学 | P2 |
| A5 | 教师可审核、编辑、上架/下架病例 | P2 |

#### 模块 B：AI 患者仿真

| 需求编号 | 需求描述 | 优先级 |
|---|---|---|
| B1 | 患者 Agent 能根据学生提问，分类意图并选择对应信息层级披露事实 | P0 |
| B2 | 患者 Agent **绝不编造医学事实**，信息不足时回答"不清楚/不知道" | P0 |
| B3 | 患者 Agent **绝不主动透露诊断或治疗方案**（Tier 4 信息永久隐藏）；若学生追问"之前医生怎么说的"，可模糊复述已被告知的信息（如"医生说牙根发炎了"，而非 ICD 编码或完整诊断名） | P0 |
| B4 | 患者 Agent 能识别医学术语，对听不懂的专业词汇表达困惑 | P1 |
| B5 | 同一病例可通过调节人格参数（焦虑程度、话量、信任度、语言风格）产生自然的表达差异 | P1 |
| B6 | 同一病例对不同学生的开场白保持一致（确保考核公平性） | P1 |
| B7 | 支持流式输出回答（token-by-token streaming），模拟真实患者逐句说话的自然感 | P0 |
| B8 | 支持处理学生连续多问（仅回答第一个问题，追问"还有呢？"等引导学生逐一提问） | P2 |

#### 模块 C：问诊对话

| 需求编号 | 需求描述 | 优先级 |
|---|---|---|
| C1 | 学生通过 Web 界面进行自然语言问诊对话，支持流式实时渲染（token-by-token） | P0 |
| C2 | 对话轮数有上限控制（默认不超过 12 轮，对标口腔执医 Station 4 考试 15–20 分钟时间约束下的平均问诊轮次），超过后提示提交诊断 | P1 |
| C3 | 对话记录完整保存，支持历史回放（只读模式，含时间戳和轮次标记） | P1 |
| C4 | 支持中途结束会话（区分"正常结束"与"主动放弃"两种状态） | P2 |

#### 模块 D：诊断提交

| 需求编号 | 需求描述 | 优先级 |
|---|---|---|
| D1 | 学生提交结构化的诊断报告：主诊断、鉴别诊断、诊断依据、建议检查、治疗方案 | P0 |
| D2 | 表单支持自动草稿保存 | P2 |

#### 模块 E：智能评估

| 需求编号 | 需求描述 | 优先级 |
|---|---|---|
| E1 | 系统自动对学生的诊断报告进行评分（对标口腔执医 Station 4 标准） | P0 |
| E2 | 系统自动对学生的问诊沟通能力进行评分（对标 MAAS-Global 标准） | P0 |
| E3 | 评估结果包含**逐维度分数 + 具体扣分/加分理由 + 遗漏项指明** | P0 |
| E4 | 系统生成带教老师风格的**综合性文字评语**（鼓励性 + 具体改进建议） | P1 |
| E5 | 评估结果持久化存储，支持历史查看 | P1 |

#### 模块 F：用户与会话管理

| 需求编号 | 需求描述 | 优先级 |
|---|---|---|
| F1 | 学生通过工号快速登录（无需注册流程） | P0 |
| F2 | 会话历史记录与学生账号关联，可回溯查看 | P1 |
| F3 | 教师/管理员可查看班级学生的练习统计 | P2 |

### 3.3 MVP 范围定义

> 单人开发资源有限，MVP 以"支撑毕设论文核心实验"为裁剪标准，非核心功能果断裁减或降级。

| 范围 | 包含内容 | 排除内容 |
|---|---|---|
| **MVP（阶段1）** | A1, A2, B1, B2, B3, B7, C1, C2, D1, E1, E2, E3, F1 | Personality 多样性(B5)、评估文字评语(E4)、历史回放(C3)、教师管理端(F3) |
| **MVP 病例规模** | 3–5 个经过人工校验的标准化口腔病例 | 批量导入(A1 的全自动化)、病例审核流程(A5) |
| **MVP 评估** | Station 4 诊断评分 + MAAS-Global 沟通评分（逐维度打分） | 教师风格综合评语(E4) |

**MVP 裁剪原则**：
1. 完整链路优先于单一模块深度——先让"登录→问诊→评估"全链路跑通
2. 实验数据优先于用户体验——能产出消融实验数据的 feature 优先于锦上添花的 feature
3. 准确性优先于多样性——零幻觉 > 多种人格 > 花哨 UI

## 四、数据资源盘点

### 4.1 已持有的数据资产

| 数据资源 | 位置 | 规模 | 状态 | 用途 |
|---|---|---|---|---|
| **原始口腔门诊病历** | `local/medical_records.csv` | 2,124 条原始门诊记录（1.59 MB） | 本地私有，不进 Git | 病例库的原始数据源 |

### 4.2 病例数据特征

> ⚠️ **重要特征**：病例文本主体为**英文临床描述**（如 "protruding teeth, consultation for correction", "chronic periapical periodontitis acute exacerbation"），但以**中文结构化标签**组织（如"主诉/就诊原因："、"现病史："、"口腔检查："）。推测原始数据来自双语或英文诊所环境。系统的 prompt、UI、对话均为中文，Agent 需具备在英文病例事实基础上用中文自然表达的能力。

每条病例包含以下自然语言字段（中文标签 + 英文内容混合格式）：

```
基本信息：性别、年龄
就诊类型：首诊 / 复诊
主诉/就诊原因：患者的就诊自述，一句话
现病史：OLDCARTS 框架下的详细描述
既往史：口腔既往史、全身病史、过敏史、用药史
口腔检查：视诊、叩诊、探诊、松动度、扪诊、冷热诊
辅助检查：X光/CBCT/全景片发现
初步诊断：主诊断 + 次要诊断（含 ICD 编码）
治疗计划：急症处理 + 根治方案 + 修复方案 + 注意事项
处置记录：实际执行的临床操作
医嘱：术后注意事项和复查建议
```

### 4.3 数据质量评估

| 维度 | 现状 | 风险 |
|---|---|---|
| **完整性** | 2,124 条原始记录 → 核心字段过滤 → 1,408 条合格病例（过滤率 33.7%，主要因缺少口腔检查/诊断/治疗方案）。首诊 670 例 + 复诊 738 例 | 部分病例缺少辅助检查或既往史 |
| **准确性** | 数据源自医院 HIS 系统导出，诊断和治疗方案由临床医生录入 | 存在录入不规范的变体（如同一诊断有多种写法）；病例主体为英文，Agent 需在中文对话中准确转述 |
| **隐私性** | 原始数据含真实患者信息，已通过清洗去除姓名等直接标识 | 建议部署前进行更彻底的脱敏审计 |

### 4.4 数据资产相对于需求的价值

- ✅ **口腔科问诊练习**：病例库已覆盖常见的口腔疾病（龋病、牙髓炎、根尖周炎、牙周炎、智齿冠周炎、口腔颌面感染、牙外伤等），足够支撑日常教学
- ✅ **难度分层**：病例长度从 200 字到 2000+ 字不等，自然形成了难度梯度
- ⚠️ **稀有病例覆盖**：罕见口腔疾病的病例较少，进阶教学场景不足
- ❌ **多科室扩展**：当前仅有口腔科数据，扩展到其他科室（内科、外科等）需要新的数据源

## 五、环境与基础设施

### 5.1 运行环境

| 维度 | 当前条件 | 约束 |
|---|---|---|
| **操作系统** | Windows 11（开发机） | 部署时可能需要 Linux server |
| **Python 版本** | 3.10+ | 部分依赖（FAISS）对 Python 版本敏感 |
| **Node.js 版本** | 18+ | 前端构建需要 |
| **包管理** | pip + npm | 无 Poetry/Pipenv 等锁定方案 |
| **数据库** | SQLite（本地文件） | 单机开发足够，多用户并发需迁移到 PostgreSQL |
| **Embedding 模型** | BGE-large-zh-v1.5（本地 sentence-transformers）或者阿里百炼API | GPU 加速，1024 维，镜像 `hf-mirror.com` |
| **LLM API** | 阿里百炼 DashScope（OpenAI 兼容接口） | 需要稳定的 API Key 和网络连接 |

### 5.2 LLM 依赖

| 模型角色 | 当前使用模型 | 调用场景 | 每轮调用次数 |
|---|---|---|---|
| **主力推理模型** | `deepseek-v4-pro`（阿里百炼） | Patient 回答生成、评估评分、教师评语 | 2–3 次 |
| **轻量分类模型** | `qwen3.6-flash`（阿里百炼） | 意图分类、事实校验 | 1–2 次 |
| **Embedding 模型** | `BGE-large-zh-v1.5`（本地部署）或者阿里百炼API | 向量检索（v3 已废弃，保留兼容） | 按需 |

> 💡 使用国产大模型 API 已经大幅降低成本：主力模型 deepseek-v4-pro 价格约为 GPT-4o 的 1/10–1/5，轻量模型 qwen3.6-flash 更为低廉。

### 5.3 成本估算（基于当前国产模型配置）

| 场景 | 调用量 | 预估成本 |
|---|---|---|
| **单次问诊（12 轮）** | 约 36 次 LLM 调用（意图分类×12 + 回答生成×12 + 事实校验×12） | 约 ¥0.5–2（含主力 + 轻量模型） |
| **单次评估** | 约 3 次 LLM 调用（Block A + Block B + Teacher Comment） | 约 ¥0.1–0.5 |
| **学期教学（200 学生 × 5 次练习）** | 约 36,000+ 次 LLM 调用 | 约 ¥500–2,000/学期 |

> 💡 相比 GPT-4o 方案，当前国产模型配置可降低约 90% 的 API 费用。Embedding 使用本地模型，进一步节省成本。

### 5.4 外部服务依赖

| 服务 | 用途 | 可用性要求 |
|---|---|---|
| **LLM API Provider** | 所有 AI 能力的底层服务 | 99%+ 可用性，<3s 响应 |
| **无其他外部服务** | — | — |

> 当前架构不依赖任何第三方 SaaS（如数据库云服务、消息队列等），是**纯本地 + API 的单体架构**，部署复杂度极低。

## 八、实验设计方案

> 毕设论文的核心环节。实验设计应在代码实现之前完成，确保系统实现服务于实验目标，而非反过来。

### 8.1 核心研究问题

| 编号 | 研究问题 | 对应实验 |
|---|---|---|
| RQ1 | 结构化字段查找能否显著降低幻觉率（相比纯 RAG 基线）？ | 消融实验 A |
| RQ2 | 事后事实校验对幻觉率的边际贡献有多大？ | 消融实验 B |
| RQ3 | 双轨评估（Station 4 + MAAS-Global）的评分与人类专家评分的一致性如何？ | 一致性实验 |
| RQ4 | 不同人格参数下的患者 Agent 对学生学习体验的影响？ | 用户体验实验（可选） |

### 8.2 消融实验设计

**基线系统定义**：

| 变体 | 事实获取方式 | 事实校验 | 预期幻觉率 |
|---|---|---|---|
| **Vanilla LLM** | 仅靠 LLM 参数化知识 | 无 | ~40%（参照已有文献） |
| **+ RAG** | 向量检索 + LLM 生成 | 无 | ~20–30% |
| **+ Structured** | 结构化字段查找（本系统方案） | 无 | ~8–15% |
| **+ Structured + Verifier** | 结构化字段查找 | 事后事实校验 | <5%（目标） |

**实验流程**：
1. 选取 5 个标准化病例，每个病例 5 条标准问诊轨迹（共 25 条轨迹）
2. 对每条轨迹，在 4 种变体下各运行 3 次（总计 300 次问诊）
3. 对 AI 患者的每条回答标注"事实正确 / 事实错误 / 信息不足正确拒绝"
4. 计算各变体的幻觉率、正确拒绝率、信息充分度

**评估指标**：
- **幻觉率** = 含事实错误内容的回答数 / 总回答数
- **正确拒绝率** = 对超出 Tier 1–3 信息范围的提问正确回答"不清楚/不知道"的比例
- **信息充分度** = 在信息范围内充分回答的比例

### 8.3 评估一致性实验

**实验流程**：
1. 招募 3 位口腔临床带教老师作为评审
2. 选取 10 份学生问诊记录，每份包含完整的问诊对话 + 诊断报告
3. 3 位老师各自独立评分（Station 4 各维度 + MAAS-Global 各维度 + 总体印象分）
4. 系统对同一批 10 份记录进行双轨评分
5. 计算 ICC（组内相关系数）、Pearson r、Cohen's κ

**预期结果**：系统与人类专家评分的 ICC ≥ 0.75（良好一致性），Pearson r ≥ 0.80。

### 8.4 实验成本估算

| 实验 | 调用量估算 | 预估成本 |
|---|---|---|
| 消融实验（300 次问诊 + 评估） | 约 12,000 次 LLM 调用 | 约 ¥150–400 |
| 一致性实验（10 份记录 × 评估） | 约 30 次 LLM 调用 | 约 ¥3–15 |
| 预实验与调试 | 约 5,000 次 LLM 调用 | 约 ¥100–300 |
| **合计** | | **约 ¥250–700** |

> 实验阶段优先使用 `qwen3.6-flash` 跑消融实验的低成本变体，仅在最终一致性实验中使用主力模型。消融实验中 Vanilla LLM 和 RAG 变体不需要事实校验步骤，实际调用成本低于完整系统。

## 九、关键约束与风险

### 9.1 技术约束

| 约束 | 影响 | 缓解方案 |
|---|---|---|
| **LLM API 是唯一的外部依赖** | API 不可用时系统完全不可用 | 本地部署开源模型作为备份（如 Qwen、DeepSeek）；离线降级提示 |
| **LLM 存在固有不确定性** | 同样的输入可能产生微妙差异 | 关键步骤（意图分类、事实校验）使用 temperature=0；开场白做确定性缓存 |
| **SQLite 不支持高并发写入** | 多学生同时问诊时可能写入阻塞 | 开发/演示阶段可接受；部署阶段迁移 PostgreSQL |
| **流式输出中途出错无法撤回** | 事实校验在生成之后，如果校验失败，已流出的 token 无法纠正 | 在 prompt 层面强化约束以减少校验失败概率；日志记录供后续分析 |

### 9.2 业务风险

| 风险 | 严重程度 | 应对 |
|---|---|---|
| **AI 患者编造症状（幻觉）** | 🔴 高 | 通过结构化字段查找（非 RAG）+ 事后事实校验控制风险 |
| **评估评分与实际临床能力不一致** | 🟡 中 | 需要人类专家 vs LLM 评分一致性实验|
| **学生过度依赖或"背诵"AI 患者的回答模式** | 🟢 低 | 通过 Persona 系统制造表达差异，防止机械记忆 |
| **原始病例数据的隐私合规风险** | 🟡 中 | 清洗姓名等标识；部署前需做更全面的脱敏审计 |
| **医院方对 AI 替代 SP 的接受度** | 🟡 中 | 定位为"补充练习工具"而非"替代真人 SP"；汇报时强调辅助教学定位 |

### 9.3 项目管理风险

| 风险 | 影响 | 应对 |
|---|---|---|
| **单人开发，无团队 backup** | 开发进度完全取决于个人时间投入 | 合理规划 MVP 范围，非核心功能果断裁减 |
| **毕设与医院演示两条线并行** | 精力分散，两个都可能做不好 | 明确优先级：毕设论文 > 医院演示 > 求职 Demo |
| **LLM API 费用超出预期** | 毕设实验成本失控 | 实验阶段优先使用廉价模型（lite）；批量实验前做单次成本估算 |

## 十、与同类工作的差异化定位

| 对比维度 | 传统真人 SP | 简单 LLM Chat | PatientAgent |
|---|---|---|---|
| **事实准确性** | 依赖 SP 记忆（有偏差风险） | 纯 RAG（幻觉率 ~40%） | 结构化字段查找（幻觉率 <5%） |
| **表达多样性** | 不同 SP 自然不同 | 单一风格 | 多维度人格组合（焦虑程度×话量×信任度×语言风格，3³×3=81 种参数组合），可控可调节 |
| **可用性** | 预约制，每学期 2–3 次 | 随时可用 | 随时可用 |
| **评估反馈** | 依赖教师主观评分 | 无评估或简单打分 | 双轨量化评估 + 逐维度反馈 |
| **成本（边际）** | 高（人力成本） | 中（API 调用） | 中（API 调用，但 lite 模型降本） |
| **可扩展性** | 受 SP 人数限制 | 理论无限 | 理论无限（多科室仅需加病例数据） |
