# 病人模拟阶段 · 现状与路线图

> 2026-10-09 整理。这是当前阶段（**病人模拟**）的入口文档，取代此前多份散落文档。
> 评分/评估、前端、persona、数据解耦等已归档至 `old_docs/`。
> 工程细节（耦合、前后端、中间件、延迟分流）不在本阶段考虑范围内。

## 1. 项目定位（一句话）

LLM 驱动的虚拟标准化患者（SP）教学平台：口腔医学生与 AI 患者对话练习临床问诊，患者按学生提问**分级披露**病史/症状/检查结果，学生自行诊断。
**本阶段只做一件事：把"患者"演得像真的。**

## 2. 现状盘点

### 已有（能跑）
- 后端 FastAPI + SQLite 全链路代码完整：登录 → 病例 → 问诊 SSE → 诊断提交 → 评估 → 历史。
- 病人 Agent 4 步流水线在 `backend/agent/`：意图分类 → 信息检索（纯 Python）→ 回答生成 → 事实校验。LLM = 阿里百炼（`deepseek-v3.1` pro + `qwen-turbo` lite，已验证可用）。
- 前端 React 页面齐全。

### 缺口（硬阻塞）
- DB `cases` 表 0 行 → 病例列表为空。旧病例只有 `data/cases/mvp_cases.json`（3 例，旧 schema，与新版数据不匹配）。

### 关键新输入
- `Oral_Agent_SP_Development_Cases30_v2.docx`：医生提供的 30 例病例 + 行为测试 + 评分依据，新 schema（v2.1）。**这是后续全部工作的数据基础。**

## 3. 核心需求（聚焦病人模拟）

1. 学生像真实问诊一样提问，患者像真实病人一样回答。
2. **分级披露**：主诉开场即给；一般病史学生问才给；检查结果学生"申请检查"才给；诊断/治疗永不透露。
3. **防幻觉**：回答只能来自病例事实，不能编造。
4. **抗错误前提**：学生对错误前提（如错侧别、错牙位）提问时，患者礼貌纠正，不因学生坚持而改口。
5. **缺失 ≠ 阴性**：问及病例未设定的信息 → 标记资料不足，不能默认成"患者否认"。
6. **语言可改，事实固定**：医学事实锁死，措辞可口语化。

## 4. 当前 Agent 架构（病人侧）

`backend/agent/patient_agent.py` 编排 4 步：

```
学生提问
  → ① 意图分类（LLM lite, temp=0）：这句话想问什么
  → ② 信息检索（纯 Python，无 LLM）：查表决定给哪些事实
  → ③ 回答生成（LLM pro, temp=0.3, 流式）：把事实口语化
  → ④ 事实校验（LLM lite, temp=0）：回答是否越界（事后审计，不撤回）
```

**核心机制**：第 ② 步是防幻觉的关键 —— 不该给的事实根本不进入上下文，模型无从编造。

## 5. 新数据（30 例）的结构

文档 v2.1，30 例分 5 组：牙体牙髓 8（EN01-08）、牙周 6（PE01-06）、修复 6（PR01-06）、黏膜 2（MU01-02）、颌面外科 8（SU01-08）。无儿童组。均为 LLM 合成的教学初稿（标记 split=development，尚未经过真实运行验证）。

### 每例的组成（编号体系）

| 编号 | 含义 | 谁可读（角色） |
|---|---|---|
| H01–H07 | 患者事实（主诉/发展/鉴别症状/全身/诊疗史/健康风险/习惯） | 患者 |
| P01–P03 | 心理（担忧/偏好/理解与反应） | 患者 |
| 开场白 | 患者开场主诉 | 患者 |
| E01–E0n | 检查项目（含别名、可接受申请表达、返回的文字结果） | 检查 |
| D01/D02、DD | 诊断/诊断理由/鉴别 | 评价（教师） |
| T01–T03、G01/G02 | 诊疗计划/沟通参考 | 评价（教师） |
| R01–R14 | 14 项 0–2 分评分锚点（本阶段不做） | 评价 |
| B01–B12 | 12 个固定行为测试（360 条，均未运行） | 测试者 |
| S01–S02 | 2 条多轮脚本（60 条，均未运行） | 测试者 |

### 四角色权限（文档明确要求"分角色文件 + 权限控制"）

| 角色/文件 | 可读 | 不可读 |
|---|---|---|
| 患者 `02_patient_runtime` | H、P、开场白、本轮听到的解释 | E 全文、D/DD/T/G/R、B 预期答案 |
| 检查 `03_exam_runtime` | 本 case 的 E、别名、已有结果、缺失状态 | 教师评分、其他病例 |
| 评价 `04_evaluator_reference` | 日志、学员作答、E 披露轨迹、R 规则 | 学员的人类评分 |
| 测试者 `05_behavior_tests` | B/S 输入、固定历史、预期/禁止行为 | — |

### 关键披露规则（文档 §披露与缺失）
- 开放式询问允许自然叙述 H01–H04，**不把正常开放式问诊当作弊**。
- 针对性追问只给对应事实，不一次报出全部病史。
- 牙位编号是后台定位用；患者按侧别/区域表达，不主动说检查编号、毫米数、诊断。
- 未设定事实 → `NEEDS_CASE_COMPLETION`（资料不足），不能默认成否认；H 里明确"不详"才用不确定口吻。
- 检查用"相关表达召回"：命中确认类表达返回对应 E 整包，明确"已做/未做"状态；显式方法有专属 E 时优先。

### 病例标题含诊断 —— 绝不能进患者上下文
文档明示：主题标题（如"冷甜刺激短痛：36深龋相关可复性牙髓炎"）**仅供教师**；学生界面只显示中性病例编号 + 开场主诉。拆数据时标题必须隔离到评价文件，绝不能进 `patient.json`。

## 6. 本阶段聚焦 / 不聚焦

**做（都是"学生看到的病人"）**：
- 患者模块：H/P + 开场白 + 分级披露 + 披露轨迹
- 检查模块：E 的别名匹配 + 返回文字结果

**不做（推迟）**：
- R01–R14 评分、评价器、`reference.json` 里的 D/DD/T/G 答案锚点
- 前端改动、解耦、中间件、延迟等工程项

## 7. 数据要做的处理

目标：把 docx 拆成四份角色文件，程序按角色加载。

1. **冻结快照**：docx 与提取文本落一份到 gitignored 的 `data/raw/`，此后不再以 docx 为准。
2. **无损解析**：docx → 结构化 JSON（保真：别名表、E 子项、H/P/E/D/R/B/S 全部字段）。
3. **引用完整性校验**：R 锚点引用的 H/E/D 编号是否都存在；别名表是否完整；B 预期行为引用的"病例事实"编号是否指向真实条目。
4. **角色拆分**：产出 `patient.json` / `exam.json` / `reference.json` / `tests.json`（本阶段实际只用前两个）。
5. **3 例人工核对**：EN01（基础）/ PE01（基础）/ SU05（安全关键）逐字段比对原 docx，确认保真。

## 8. 分步落地

- **里程碑 1 — 3 例拆出来能看见**：解析 EN01/PE01/SU05，产出分角色 JSON，人工核对。
- **里程碑 2 — 单例患者对话跑通**：患者模块改造为"事实选择 → 披露门控 → 生成 → 披露轨迹"，只加载 `patient.json`。验收 = EN01 的 B01–B08、B11、B12。
- **里程碑 3 — 检查模块**：别名匹配 + 子项裁剪 + 未命中记录。验收 = B09、B10。
- **里程碑 4 — 扩到全 30 例**：跑全量 B 测试，收集未命中表达回给医生补词表。

安全测试（B06 抗错误前提、B08 越权隔离、B10 缺失不编造）在里程碑 2 第一批就跑，不等功能全绿。

## 9. 验证方式

- **确定性测试**（别名匹配、披露门控）：纯 Python，零 LLM，可断言。
- **行为测试 B01–B12**：每例规格注明"发送内容 → 预期行为 → 禁止行为 → 对应病例事实编号"，直接断言系统解锁的 H/E 编号是否正确，而非靠人读文本判断。每条独立跑 3 次，按核心语义判稳定，不逐字比对。
